# 設計書：FF14 パッチノート Q&A

最終更新: 2026-11-17

## 1. 全体の構成

```text
[ロードストーン]
     │ ① 取得（23ページを1回だけ）
     ▼
data/raw/lodestone/*.html
     │ ② 本文と表を取り出して分割
     ▼
data/processed/chunks.jsonl（2,932チャンク、うち PvP 403）
     │ ③ 埋め込み（512トークンを超えるチャンクは、埋め込みのときだけ pieces に分ける）
     ▼
data/index/（Chroma。チャンクのコレクションと、pieces のコレクション）
     │
     ▼
[FastAPI  POST /ask]
     │ ④ 検索（PvE／PvP で絞り込み、vector または hybrid。意味の近さは pieces で探してチャンクに戻す。hybrid では質問のジョブと合う資料の順位を上げる）
     │ ⑤ プロンプトを選ぶ（auto: 質問の言葉で v4 か v5）
     │ ⑥ AI で回答（llm.py。今は Gemini）
     │ ⑦ 今の値をコードで決め直す（auto のとき）
     ▲
     │ /api/ask（Vite のプロキシ）
[React の画面]
```

| 役割 | 使うもの |
| --- | --- |
| バックエンド | Python 3.12、FastAPI、uvicorn |
| HTML の解析 | Beautiful Soup |
| 埋め込み | intfloat/multilingual-e5-small（sentence-transformers） |
| ベクトルDB | Chroma（ローカルに保存） |
| キーワード検索 | rank-bm25（2文字ずつの区切り） |
| 回答 | Gemini API（google-genai）。llm.py で会社ごとに呼び分けられる形にしている |
| 自動テスト | pytest、GitHub Actions |
| フロントエンド | TypeScript、React、Vite、ESLint、react-markdown |

## 3. データの流れ

### 3.1 取得（fetch_lodestone.py）

- パッチノート一覧ページに載っている 7.x の23本の URL を、コードに直接書いている
- 1ページごとに5秒あける。保存済みのページは取りに行かない
- User-Agent に個人のポートフォリオ用と分かる文字を入れる

### 3.2 分割（extract_chunks.py）

本文の入れ物は `div.news__detail__wrapper`。見出しは、タグ名と class で次の階層に分ける。

| 階層 | タグ | 例 |
| --- | --- | --- |
| 0 大分類 | h3.mdl-title__ancher | バトル関連、アイテム関連 |
| 1 中分類 | h2 | PvP全般、クエスト関連 |
| 2 項目 | その他の h3 | アクション／特性において、以下の調整が行われます。 |
| 3 ジョブ名など | h4 | モンク |
| 4 | h5 | |

分割のルール:

- 同じ見出しの下にある段落と表を、1,500文字を目安にまとめる
- 表は Markdown の表に変換し、途中で切らない。1,500文字を超える表だけ行の区切りで分け、分けたそれぞれに見出しの行を付け直す
- すべての行が空の列（矢印の画像だけの列）は消す
- 項目以下（階層2以上）の見出しの下に本文も表もなければ、見出しの文を本文として残す
- 各チャンクの先頭に「[パッチ7.2] バトル関連 > … > モンク」の形でパッチ番号と見出しを付ける

チャンクの形（chunks.jsonl の1行）:

| フィールド | 内容 |
| --- | --- |
| id | 「パッチ番号-順番」（例: 7.2-0025）。チャンクの作り方を変えると番号がずれる |
| version | パッチ番号（文字列） |
| order | パッチ番号（数値）。7.05 < 7.1 < 7.11 < 7.2 の順に並ぶ |
| headings | 見出しの階層 |
| has_table | 表を含むか |
| url | 元記事の URL |
| text | 検索と回答に使う本文 |

### 3.3 埋め込み（build_index.py）

- 文書には「passage: 」、質問には「query: 」を付ける（e5 系のモデルの決まり）
- ベクトルは正規化し、Chroma にはコサイン距離で保存する
- 見出しに PvP 系の言葉があるチャンクに `is_pvp` の印を付ける
- 作り直すたびに古いデータを消してから入れ直す

チャンクのコレクション（patch_notes）のほかに、pieces のコレクション（patch_notes_pieces）を作る。

- 埋め込みのモデル（multilingual-e5-small）は512トークンまでしか読まず、それより後ろは切り捨てる。分割のルールが「1,500文字を目安」なので、PvE のチャンク 2,529件のうち 332件が512トークンを超えていた（PvP は0件）。長いチャンクの後ろのほうにある行は、意味の近さの検索から見えていなかった
- そこで、埋め込みのときだけ、512トークンを超えるチャンクを、512トークン以内の pieces に分ける（rules.py の split_for_embedding）
  - チャンクの1行目（「[パッチ…] …」の見出しの行）を、すべての piece の先頭に付ける
  - 2行目から後ろを、行の区切りで前から順に詰める。1行だけで512トークンを超える行は、切らずに、その行だけで1つの piece にする
  - トークンは、埋め込みのモデルのトークナイザーで、実際に埋め込む文（「passage: 」付き）を、特別なトークンを含めて数える
- piece の ID は「チャンクの ID#番号」（例: 7.05-0018#2）。metadata は parent_id（元のチャンクの ID）と is_pvp
- 512トークン以内のチャンクは、そのまま1つの piece になる
- pieces は 3,395個（分けたチャンクは332件）。512トークンを超える piece は0個
- チャンク、チャンクの ID、キーワードの検索、AI に渡す資料は変えていない。pieces は意味の近さの検索だけに使う

### 3.4 検索（app/rag.py の search）

1. 質問に PvP 系の言葉があれば PvP のチャンクだけ、なければ PvP 以外のチャンクだけを対象にする
2. 検索のしかたに応じて、上位8件を選ぶ（画面では hybrid を使う）
   - vector: 意味の近さの上位8件
   - hybrid: 意味の近さの上位30件と、キーワード検索（BM25、2文字ずつの区切り）の上位30件を、RRF（定数60）で合わせる。質問のジョブと、チャンクの見出しのジョブが合えば、点数に JOB_BONUS（1/61）を足す。その上位8件
3. それぞれに検索での順位（rank）と意味の近さ（score）を付け、パッチの古い順に並べ替えて返す（変更の流れを AI が追いやすくするため）

意味の近さの検索に使うコレクションは、定数 VECTOR_INDEX で選ぶ（今は "pieces"）。

| VECTOR_INDEX | 意味の近さの検索 |
| --- | --- |
| pieces（今） | pieces から CANDIDATES の3倍（90件）を取り、parent_id で親のチャンクにまとめ、上から30件のチャンクにする。意味の近さ（score）は、そのチャンクの piece の中で一番近いものの値 |
| chunks | チャンクを丸ごと埋め込んだコレクションから30件を取る（改善11より前の動き） |

- そのあとの RRF、JOB_BONUS、上位8件の選び方は、どちらでも同じ
- VECTOR_INDEX = "chunks" に戻せば、前の動きになる

ジョブの扱い（rules.py の job_names_from_headings、jobs_in、job_of、fuse_ranks）:

- ジョブの名前はコードに書かず、起動したときにチャンクの見出しから作る。新しいジョブが増えても、そのパッチノートを取り込めば入る
  - ジョブの調整の見出し（「アクション」と「において」を含む）の下の、一番下の見出しを「／」で分ける（例:「格闘士／モンク」）
  - 「新たなジョブ「〇〇」」「リミテッドジョブ「〇〇」」の見出しから名前を取り出す（魔獣使い）
  - 1つの見出しに新しいジョブが2つ以上あるときは、すべて取る（NEW_JOB_ALL_NAMES = True。改善14）。「新たなジョブ「ヴァイパー」「ピクトマンサー」」のように、すぐあとに続く「」の並びだけを取る。間は何もないか、「と」「、」「・」のどれか1文字。前は1つ目（ヴァイパー）しか取らず、ピクトマンサーは 7.1 の調整の見出しから入っていた。8.0 で新しいジョブが2つ出て、8.0 にそのジョブの調整の見出しがなければ、2つ目の名前が入らないため。今のデータでは名前の一覧は28個のままで変わらない
  - ロールの名前（DPS、ヒーラー、タンク、英字だけのもの）と「共通」は外す。ロールの見出しは、ジョブの調整と同じ見出しの下にあるため、言葉で外すしかなかった
  - 7.0 より前に追加され、データから取れないジョブ（青魔道士）だけは、コードに書く（OLDER_JOBS）
  - 今は28個（バトルジョブ21、クラス5、魔獣使い、青魔道士）
- 質問のジョブは、質問に出てくる名前が1つだけのときに決める。0個や2個以上なら、点数は足さない
- 合わない資料は外さない・下げない。候補の60件にない資料は足さない
- ジョブの調整の節で、見出しからジョブが見つからない資料（ロールや共通の調整。PvE 2件、PvP 12件）には、点数を足さない。そのため、正解がロールの資料にある問題では、正解が押し下げられる（7章を参照）

ジョブで検索を絞り込む方法は、試して取り消した（6章、7章、notes.md を参照）。

ロールや共通の資料の扱いを変える定数（どちらも試して取り消した。コードは残し、今は False。5.6 を参照）:

| 定数 | True のときの動き | 今 |
| --- | --- | --- |
| ROLE_SKILL_BOOST（改善12） | ロールや共通の資料の、表や箇条書きのスキル名が質問の中にあれば、その資料にも JOB_BONUS を足す（rules.py の boosted_chunks） | False |
| ROLE_HEADING_JOBS（改善13） | AI に渡すときだけ、ロールや共通の資料の見出しの行にジョブ名を書き足す（「ヒーラー」→「ヒーラー（白魔道士／学者／占星術師／賢者）」、「共通」→「共通（すべてのジョブ）」）。ロールとジョブの対応は、ロールクエストの見出し（「≪ヒーラー（白魔道士／…）≫」）から作る（rules.py の role_jobs_from_headings、label_role_heading）。検索は変えない | False |

- 定数1つで試し直せる。2つを両方 True にした形は、まだ測っていない

### 3.5 回答（app/rag.py の answer）

ルール:

| 名前 | 内容 | 使うプロンプト |
| --- | --- | --- |
| RULES | 資料にないことは答えない／同じ項目が複数のパッチで変わっていたら一番新しいものを今の情報とする／PvE と PvP を区別する／根拠のパッチ番号を書く | v1、v2、v5 |
| RULES_HISTORY | RULES の2行目だけを「上書きされた変更も省略せず、古い順にすべて書く」に入れ替えたもの | v4 |

プロンプト:

| 名前 | 内容 | 状態 |
| --- | --- | --- |
| v1 | RULES だけを伝えて、すぐに答えさせる | auto では使っていない。前の結果と比べるために残している |
| v2 | 数値の今の値を聞かれたら、項目を1つに決め、経緯を古い順に書き出してから答えさせる | auto では使っていない。前の結果と比べるために残している |
| v3 | 質問の種類を AI に決めさせ、種類ごとに答え方を指示する | 使っていない（今の値を間違えるようになった） |
| v4 | v1 のルールを RULES_HISTORY に入れ替えたもの | 何が変わったか・いつ変わったかの質問に使う |
| v5 | v2 の手順の1と2に、「質問されたジョブ・スキルの資料だけを使う。別のジョブや別のスキルの資料は、同じ項目が書かれていても使わない」を足したもの | 今の値の質問に使う |
| auto | 質問の種類をコードで決めて、v4 か v5 を使う | 画面で使う |

auto の流れ:

1. 質問に「何が変わ」「どう変わ」「どう調整」「変更点」「変更内容」「どのパッチ」「いつ」のどれかがあれば v4、なければ v5 を使う
   - 判定は rules.py の choose_prompt。経緯の質問には "v1"、それ以外には "v2" を返す
   - rag.py の pick_prompt が、"v1" を AUTO_HISTORY_PROMPT（"v4"）に、"v2" を AUTO_CURRENT_PROMPT（"v5"）に置き換える。前の結果と比べるときは、この2つを "v1"、"v2" に戻す
   - answer と show_context.py の両方が pick_prompt を使う。表示されるプロンプトと実際に使うプロンプトがずれないようにするため
2. llm.py の generate で回答を作る（3.6 を参照）
3. 回答に【変更の経緯】の行があれば、一番新しいパッチの「変更後」を【今の値】に入れ直す（rules.py の fix_current_value）。パッチ番号は数値として比べる
4. 拡張パッケージの境目を確かめる（rules.py の guard_expansion。EXPANSION_GUARD = True。改善14）。下を参照
5. 結果には、どのプロンプトを使ったかを「auto(v4)」「auto(v5)」の形で残す

拡張パッケージの境目の確認（EXPANSION_GUARD）:

- なぜ要るか：7.0 のジョブのスキルの調整は、パッチノートの本文になく、「詳しくは『 こちら 』をご覧ください。」のリンクの先（ジョブガイド、jp.finalfantasyxiv.com/jobguide/battle/）にある。そのため、今の取り込み方では、7.0 のスキルの調整は1行もデータに入っていない。8.0 も同じ作りなら、8.0 でスキルが作り直されても、データには「こちら」しか入らず、7.x の最後の変更の値を今の値として答えてしまう
- 対象：今の値の質問（auto で v5 を使ったもの）で、質問にジョブ名があるもの（job_of が None でない）。PvE と PvP の両方。経緯の質問は対象にしない
- どう動くか：fix_current_value と同じく、【変更の経緯】の中で一番新しいパッチを根拠のパッチとし、その版の先頭の数が最新の拡張パッケージより小さいとき、【今の値】の行を「分かりませんでした（最後の変更はパッチX.XXですが、そのあと拡張パッケージY.0でスキルが作り直された可能性があり、パッチノートだけでは今の値を確かめられません）」に差し替える。【変更の経緯】はそのまま残す
- 最新の拡張パッケージは、取り込んだチャンクの版から作る（rag.py の newest_expansion。rules.py の latest_expansion）。コードに 8 などを書かない
- 差し替えは AI の答えを受け取ったあとにコードで行うので、AI に渡すプロンプトは変わらない
- 今のデータは 7.x だけで、最新の拡張パッケージは 7 なので、答えは1問も変わらない。効き目は作り物の 8.x のデータの自動テストで確かめ、rag.answer() につながっているかは、保存した答えを返す偽物の generate で、AI を呼ばずに確かめた（newest_expansion を 8 にすると、予想した40問で【今の値】の行だけが替わった）

### 3.6 AI を呼ぶ部分（app/llm.py）

- 会社ごとにクラスを1つ持つ。クラスには、名前（name）、試すモデルの一覧（models）、1回呼ぶ処理（complete）を持たせる
- 今あるのは GeminiProvider だけ（gemini-3.8-flash → gemini-3.5-flash-lite の順に試す。temperature 0）
- 使う会社は .env の LLM_PROVIDER で決める。書かなければ gemini。知らない名前ならエラーにする
- generate は、モデルを先頭から順に試す
  - 各社のクラスは、混雑や回数制限（Gemini では 429、500、503）を RetryableError に直して出す。このときだけ次のモデルを試す
  - それ以外のエラーは、次のモデルを試さずにそのまま出す
  - すべて失敗したら LLMUnavailableError を出し、API は 503 を返す
- Gemini のライブラリと API キーは、最初に AI を呼ぶときに読み込む。自動テストでは Gemini のライブラリを入れていないため
- main.py と run_eval.py は、今までどおり rag.py から LLMUnavailableError を読み込む（rag.py が llm.py から読み込み直している）
- 別の会社を足すときは、同じ形のクラスを llm.py に作って PROVIDERS に足し、requirements.txt にライブラリを、.env にキーを書く。検索、プロンプト、rules.py、採点、画面は変えなくてよい

### 3.7 画面（frontend）

- 回答に【今の値】の行があれば取り出し、「値（根拠: パッチ〇〇）」を値と根拠に分けて大きく表示する。残りは react-markdown で表示する（HTML はそのまま実行しない）

## 4. 評価と自動テスト

### 4.1 評価（run_eval.py）

| オプション | 内容 |
| --- | --- |
| --model | 使うモデルを1つに固定する（モデルを比べるとき） |
| --prompt | v1 / v2 / v3 / v4 / v5 / auto |
| --search | vector / hybrid |
| --search-only | AI を使わずに検索だけを測る（回数制限を使わない） |
| --questions | 使う質問のファイル（省略時は eval/questions.jsonl） |

- 1問ごとに5秒あける。混雑（429、500、503）のときは30秒待って、最大3回まで試す
- 1日の回数制限に達したときは、待っても回復しない。429 が何問も続いたら止める
- 503 で失敗した呼び出しも、回数制限に数えられることがある。503 が続いたら1問目で止める
- 結果のファイル名: 「日時_（質問のファイル名_）モデル_プロンプト_検索.jsonl」
- 答えが1つも出なかった結果ファイルは消す（0点に見えてしまうため）。消したことは notes.md に書く
- 一部の問題だけが混雑でエラーになったときは、その問題だけのファイルを作って流し直す（例: retry.jsonl）

採点:

| 種類 | ◯の条件 |
| --- | --- |
| latest、other_attr_later、pvp_noise | 正解の数字が入っている。【今の値】の行があれば、その行だけを見る |
| history | 「分かりませんでした」と答えておらず、必要なパッチ番号がすべて入っている |
| when | 正解のパッチ番号が入っている |
| unanswerable | 「分かりませんでした」などと答えている |

### 4.2 テスト用の問題の扱い

- 改善を決めるのに使わない問題を、テスト用として別のファイルに持つ
- 結果を見る前にコミットする。最終形が決まってから流し、結果を見て直さない。検索だけのモードでも流さない
- 一度流したテスト用の問題は、評価用に移す。古いファイルは名前を変えて残す（test_questions_2026-10.jsonl、test_questions_2026-11.jsonl、test_questions_2026-11b.jsonl、test_questions_2026-11c.jsonl）
- 評価用に移した問題は、原因を調べてよい（t008、m007、p001〜p004）
- 次の改善を確かめるときは、新しいテスト用の問題を作り、直す前にコミットする
- 例外: テスト用の結果を見て直したところがなく、別の評価用の問題から始めた改善なら、同じテスト用の問題をもう1回使ってよい。使う前に、その判断を notes.md に書く
- 混雑でエラーになった問題だけを流し直すのは、テスト用の問題でもよい。◯✕が出た問題は流し直さない（結果を選ぶことになるため）
- 失敗の形と同じ問題は、スクリプトで資料から探す（find_shared_attrs.py、find_split_tables.py、find_common_answers.py）。正解はすべて資料の行で確かめる
- m001〜m010、p001〜p010 は1回使って評価用に移した
- 今の test_questions.jsonl は r001〜r011（PvP のロールや共通のスキル、11問）。まだ1回も流していない。ジョブ名がある質問で、正解がロールや共通の調整にある形の改善の最終形が決まったときに使い、ほかの改善のテストには使わない。ほかの改善の前には、新しいテスト用の問題を作る

### 4.3 自動テスト（pytest、GitHub Actions）

- AI やデータに依存しない処理だけを、別のファイル（app/rules.py、scripts/grading.py）に分けてテストする。モデルの読み込みも API キーも要らず、1秒かからない
- llm.py は、偽物の会社を使ってテストする（次のモデルに移ること、全部だめなら LLMUnavailableError になること、それ以外のエラーはそのまま出すこと）。本物の AI は呼ばない
- ジョブの名前の集め方は、実際のデータで余計な名前が出てきた見出し（クイックパネル、ロールアクション、HEALER など）をそのままテストに入れている
- pieces に分ける処理（split_for_embedding）は、トークナイザーの代わりに偽物の数え方を渡してテストする（短い文はそのまま、見出しの行が全部に付く、行の順番が保たれる、どの行も落ちない、1行で長すぎる行の扱い）
- ロールや共通の資料のスキル名の取り出し（表の1列目と、箇条書きの「- スキル名」の行）と、見出しへのジョブ名の書き足し（「HEALER」の読み替え、「共通」はちょうど一致するときだけ）も、データに出てくる見出しの形でテストしている
- 拡張パッケージの境目の確認（guard_expansion）と、新しいジョブの名前の取り方（new_job_names）は、作り物のチャンク（tests/fixtures。ジョブ名「テスト騎士」、スキル名「ためし斬り」なども本文も自分で書いたもの）でテストしている。8.0 や 8.01 で変更があるスキルは差し替わらないこと、7.x だけのデータではどの質問も差し替わらないこと、新しいジョブが2つあり、そのジョブの調整の見出しがない 8.0 で、2つとも名前に入ることなど
- テストは全部で93個
- これまでに見つかった不具合や失敗を、テストとして残している
  - 大分類が変わっても前の中分類が残る、見出しだけの項目が消える（チャンク作り）
  - 経緯は正しいのに今の値を間違える、パッチ番号を文字として比べる（今の値の補正）
  - 「7.2」が「7.25」に一致する、「何が変わったか」に「分かりませんでした」と答える（採点）
  - ロールや操作の説明の見出しがジョブの名前に入る（ジョブの名前の集め方）
  - 「新たなジョブ「A」「B」」の見出しから、A しか取れない（ジョブの名前の集め方）
- rag.py は埋め込みモデルが要るため、テストの対象にしていない。プロンプトや rag.py を変えたら、git diff で変えた行だけが変わっていることを確かめる（消えた行の数を見る）
- テストは rules.py の関数を直接呼ぶので、rag.py から呼ばれているかは確かめられない。rag.py の中に呼ぶかどうかの条件がある処理（guard_expansion など）は、rag.generate を保存した答えを返す偽物に差し替えて、本物の rag.answer() を AI を呼ばずに流して確かめる
- 気をつけること：rules.py の定数は、関数の引数の初めの値として、読み込んだときに1回だけ決まる（NEW_JOB_ALL_NAMES は job_names_from_headings の all_names の初めの値）。調べのスクリプトから rules.NEW_JOB_ALL_NAMES を書き換えても効かないので、引数に直接渡す。rag.py は EXPANSION_GUARD を読み込んだときに受け取るので、調べのスクリプトで切り替えるときは rules.EXPANSION_GUARD ではなく rag.EXPANSION_GUARD を替える
- 検索の仕組みを変えるときは、まず効果がない値（JOB_BONUS = 0、VECTOR_INDEX = "chunks" など）で入れて、検索だけの結果が前とすべての問題で同じになることを確かめる
- push のたびに GitHub Actions で、バックエンドのテスト（requirements-test.txt のライブラリだけを入れる）と、画面の lint・ビルドを流す
- コードを直したら、まず `python -m pytest` を流す

## 6. 設計の判断

| 判断 | 理由 |
| --- | --- |
| データは Steam ではなくロードストーンから取る | Steam は概要だけで、大型パッチも取れなかった |
| 取得の前に規約を確認し、1回だけ・5秒間隔で取る | サイトへの負荷と利用条件に配慮するため |
| 見出しの階層を class で決める | タグ名だけでは、大分類（h3）と中分類（h2）の上下が逆になる |
| チャンクに見出しの階層を付ける | どのジョブの話か、PvE か PvP かをチャンクだけで分かるようにするため |
| 表を途中で切らない | スキル名と変更前・変更後が別のチャンクに分かれると、正しく答えられない |
| 見出しだけの項目を残す | 見出しそのものが変更内容になっている項目が、全体の約4分の1あった |
| 埋め込みは無料のローカルモデル | API キーも費用もかからない。後で別のモデルと比べられる |
| PvE と PvP で検索の対象を分ける | 両方で調整されたスキルで、反対側のチャンクが正解を押し下げていた |
| ハイブリッド検索 | 意味の近さだけでは、スキル名の違いをほとんど区別できなかった |
| キーワード検索は2文字ずつの区切り | 追加の辞書が要らず、スキル名のような固有名詞に強い |
| 検索結果をパッチの古い順に並べる | 変更の流れを AI が追いやすくするため |
| 別のジョブの資料は、外さずに、質問のジョブと合う資料の順位を上げる（JOB_BONUS） | 外すと、AI に渡す8件の顔ぶれが変わり、ほかの問題の資料を押し出した（q024）。順位を上げるだけなら、正解の順位を1つも変えずに、別のジョブの資料を 87件から37件に減らせた |
| 長いチャンクは、埋め込みのときだけ pieces に分ける（チャンクそのものは分けない） | 埋め込みのモデルは512トークンより後ろを切り捨て、長いチャンクの後ろの行が意味の近さの検索で見えなかった（m007）。チャンクを分け直すと、ID、キーワードの検索、AI に渡す資料まで変わり、ほかの問題の結果も動く。埋め込みだけを分ければ、変わるのは意味の近さの検索だけで、VECTOR_INDEX を "chunks" に戻せば前の動きになる |
| ジョブの名前はコードに書かず、見出しから作る | 新しいジョブは拡張パッケージや大型パッチで増える。コードに書くと、直し忘れたジョブだけ順位が上がらず、気づきにくい |
| 点数に足す値は、試す値と選び方を先に決める | 結果を見てから値を細かく選ぶと、評価用の問題だけに合わせた値になるため |
| 回答の AI は無料枠の Gemini | 費用をかけずに始めるため。混雑に備えて予備のモデルを用意した |
| AI を呼ぶ部分を llm.py に分け、会社ごとのクラスにする | 別の会社のモデルと同じ問題で比べられるようにするため。切り替えるときに、検索やプロンプトに手を入れずに済む |
| Gemini のライブラリと API キーは、使うときに読み込む | 自動テストに Gemini のライブラリを入れずに、llm.py をテストできるようにするため |
| temperature 0 | 同じ質問になるべく同じ答えを返し、比べやすくするため |
| 質問の種類はコードで決める（auto） | AI に決めさせる v3 では、肝心の答え方の手順が崩れた |
| 今の値はコードで決め直す | AI が正しい経緯を書いたのに、今の値だけを間違えることがあった |
| 拡張パッケージの境目では、今の値をコードで控える（EXPANSION_GUARD） | 7.0 のスキルの調整はパッチノートの本文になく、AI には「作り直された」ことが資料から分からない。AI に渡すのは 7.x の変更の資料だけなので、プロンプトで頼んでも、資料にない作り直しには気づけない。根拠のパッチの版と、取り込んだ版から決まることなので、コードで決めれば答えがぶれない。経緯は残すので、利用者は最後の変更までは分かる |
| 最新の拡張パッケージは、取り込んだ版から作る | コードに 8 と書くと、9.0 のときに直し忘れる。ジョブの名前と同じ考え方 |
| 新しいジョブの見出しからは、名前をすべて取る（NEW_JOB_ALL_NAMES） | 7.0 では2つ目のジョブ（ピクトマンサー）が 7.1 の調整の見出しで入っていた。8.0 では、次のパッチが出るまで2つ目の名前が入らず、そのジョブの質問で順位が上がらない |
| 経緯の質問は、ルールを入れ替えたプロンプト（v4）で答える | 「新しいパッチを優先する」ルールが、経緯の質問では途中の変更を捨てる原因になった。今の値の質問には、このルールが必要 |
| 別のジョブの資料を使わないよう、プロンプト（v5）でも指示する | 資料が上位に残っていても、AI が使わないようにするため。v5 だけでは、lite が答えるのをやめることがあった（n005） |
| 古いプロンプトを書き換えずに、新しいプロンプトを足す | 前の結果をあとから流し直して比べられるようにするため。auto で使うプロンプトは AUTO_HISTORY_PROMPT と AUTO_CURRENT_PROMPT の2つで切り替える |
| プロンプトを選ぶ処理を1か所（pick_prompt）にまとめる | rag.py と show_context.py で別々に書くと、片方だけ直したときに、表示と実際がずれるため |
| AI を呼ばずに資料とプロンプトを見る道具を持つ（show_context.py、count_other_jobs.py） | 回数制限を使わずに、答えがおかしい原因を調べられる。q018 の原因はこれで分かった |
| 検索だけを測るモード | 回数制限を使わずに、検索の改善を何度でも試せる |
| 検索の再現率は順位で測る | 上位8件だけでは100％のままで、改善が数字に出なかった |
| 評価の根拠はチャンク ID ではなくパッチ番号で持つ | チャンクの作り方を変えると ID がずれるため |
| history の質問も採点する | 採点の対象外にしていたら、v2 で答えられなくなったことに気づけなかった |
| テスト用の質問を別に持つ | 同じ質問で直し続けると、その質問だけに効く直し方になるおそれがある |
| 使い終わったテスト用の問題は評価用に移し、新しいテスト用の問題を作る | 結果を見た問題は、もう「見ていない問題」として使えないため |
| 失敗の形と同じ問題を、スクリプトで資料から探す（find_shared_attrs.py） | 手で探すと見落とす。スクリプトが q018 そのものを見つけられることを確かめてから使った |
| 直す前に、判断の基準を決めておく | 結果を見てから基準を決めると、都合のよい解釈をしてしまうため |
| 変わる問題が少ない改善は、流す前に「1問を何回流すか」と「何回◯なら効果ありか」を決める | 改善13は、プロンプトが変わる問題が3問しかないのに、1問1回の結果で判定した。効果と軽いモデルのぶれを分けられなかった |
| 取り消した変更でも、効果がない値で残せるものはコードに残す（ROLE_SKILL_BOOST、ROLE_HEADING_JOBS） | 改善12の検索の部分は効いていた。2つを組み合わせた形などを、定数1つで試し直せるようにするため |
| 採点で見分けられない悪化は、AI を流す前に取り消してよい | ジョブでの絞り込みでは、q024 の悪化を採点では見分けられなかった（パッチ番号だけで◯になる）。回数制限を使っても判断の材料にならない |
| 3.8-flash が使えないときは lite の結果で判断する | 無料枠の 3.8-flash は混雑で答えが出ないことが多く、待つと作業が止まるため |
| AI に依存しない処理を別のファイルに分ける | モデルや API キーなしで、すぐにテストできるようにするため |
| ライブラリのバージョンを固定する | 数か月後に入れ直しても、同じ環境で動くようにするため |

#### 使う AI モデル

今は Gemini API の無料枠（gemini-3.8-flash、混雑時は gemini-3.5-flash-lite）を使っている。

無料枠の問題:

- 3.8-flash は混雑（503）と回数制限（429）で、答えが出ないことが多い。10月25日から11月5日の間に、答えが出たのは1回だけ
- そのため、v4 と v5 の改善が 3.8-flash でも効いたかを、まだ確かめられていない

決めること:

- 有料にするか。有料にするなら、評価のときだけにするか、画面のアプリも有料にするか
- Gemini の有料枠にするか、別の会社のモデルにするか

分かっていること:

- 同じモデルなら、有料でも無料でも答えは同じ。有料にして良くなるのは、エラーが減ること
- 別の会社に切り替えるときのコードの修正は、llm.py にクラスを1つ足すこと、requirements.txt、.env のキー（と LLM_PROVIDER）だけで済む。検索、プロンプト、rules.py、採点、画面は変えなくてよい
- 時間がかかるのは測り直し。プロンプトは Gemini の失敗を見ながら直してきたので、別のモデルでは答え方の癖が違う。特に、今の値の補正は「【今の値】」と「- パッチ〇〇: 〇〇 → 〇〇」の形で書かれた回答でしか効かない
- 画面のアプリを有料にすると、公開したときに、質問のたびに費用がかかる。README を見た人が無料で試せるよう、Gemini の無料枠は残したい

決めるときに確かめること:

- 各社の料金ページで、今の値段を確かめる
- 有料にするなら、予算の上限と通知を必ず設定する
