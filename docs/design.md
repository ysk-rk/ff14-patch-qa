# 設計書：FF14 パッチノート Q&A

最終更新: 2026-10-25

## 1. 全体の構成

```text
[ロードストーン]
     │ ① 取得（23ページを1回だけ）
     ▼
data/raw/lodestone/*.html
     │ ② 本文と表を取り出して分割
     ▼
data/processed/chunks.jsonl（2,932チャンク、うち PvP 403）
     │ ③ 埋め込み
     ▼
data/index/（Chroma）
     │
     ▼
[FastAPI  POST /ask]
     │ ④ 検索（PvE／PvP で絞り込み、vector または hybrid）
     │ ⑤ プロンプトを選ぶ（auto: 質問の言葉で v1 か v2）
     │ ⑥ Gemini で回答
     │ ⑦ 今の値をコードで決め直す（auto のとき）
     ▲
     │ /api/ask（Vite のプロキシ）
[React の画面]
```

| 役割 | 使うもの |
| --- | --- |
| バックエンド | Python 3.12、FastAPI、uvicorn |
| HTML の解析 | Beautiful Soup |
| 埋め込み | intfloat/multilingual-e5-small（sentence-transformers） |
| ベクトルDB | Chroma（ローカルに保存） |
| キーワード検索 | rank-bm25（2文字ずつの区切り） |
| 回答 | Gemini API（google-genai） |
| 自動テスト | pytest |
| フロントエンド | TypeScript、React、Vite、ESLint、react-markdown |

## 3. データの流れ

### 3.1 取得（fetch_lodestone.py）

- パッチノート一覧ページに載っている 7.x の23本の URL を、コードに直接書いている
- 1ページごとに5秒あける。保存済みのページは取りに行かない
- User-Agent に個人のポートフォリオ用と分かる文字を入れる

### 3.2 分割（extract_chunks.py）

本文の入れ物は `div.news__detail__wrapper`。見出しは、タグ名と class で次の階層に分ける。

| 階層 | タグ | 例 |
| --- | --- | --- |
| 0 大分類 | h3.mdl-title__ancher | バトル関連、アイテム関連 |
| 1 中分類 | h2 | PvP全般、クエスト関連 |
| 2 項目 | その他の h3 | アクション／特性において、以下の調整が行われます。 |
| 3 ジョブ名など | h4 | モンク |
| 4 | h5 | |

分割のルール:

- 同じ見出しの下にある段落と表を、1,500文字を目安にまとめる
- 表は Markdown の表に変換し、途中で切らない。1,500文字を超える表だけ行の区切りで分け、分けたそれぞれに見出しの行を付け直す
- すべての行が空の列（矢印の画像だけの列）は消す
- 項目以下（階層2以上）の見出しの下に本文も表もなければ、見出しの文を本文として残す
- 各チャンクの先頭に「[パッチ7.2] バトル関連 > … > モンク」の形でパッチ番号と見出しを付ける

チャンクの形（chunks.jsonl の1行）:

| フィールド | 内容 |
| --- | --- |
| id | 「パッチ番号-順番」（例: 7.2-0025）。チャンクの作り方を変えると番号がずれる |
| version | パッチ番号（文字列） |
| order | パッチ番号（数値）。7.05 < 7.1 < 7.11 < 7.2 の順に並ぶ |
| headings | 見出しの階層 |
| has_table | 表を含むか |
| url | 元記事の URL |
| text | 検索と回答に使う本文 |

### 3.3 埋め込み（build_index.py）

- 文書には「passage: 」、質問には「query: 」を付ける（e5 系のモデルの決まり）
- ベクトルは正規化し、Chroma にはコサイン距離で保存する
- 見出しに PvP 系の言葉があるチャンクに `is_pvp` の印を付ける
- 作り直すたびに古いデータを消してから入れ直す

### 3.4 検索（app/rag.py の search）

1. 質問に PvP 系の言葉があれば PvP のチャンクだけ、なければ PvP 以外のチャンクだけを対象にする
2. 検索のしかたに応じて、上位8件を選ぶ
   - vector: 意味の近さの上位8件
   - hybrid: 意味の近さの上位30件と、キーワード検索（BM25、2文字ずつの区切り）の上位30件を、RRF（定数60）で合わせた上位8件
3. それぞれに検索での順位（rank）と意味の近さ（score）を付け、パッチの古い順に並べ替えて返す（変更の流れを AI が追いやすくするため）

### 3.5 回答（app/rag.py の answer）

プロンプト:

| 名前 | 内容 | 状態 |
| --- | --- | --- |
| v1 | ルールだけを伝えて、すぐに答えさせる | 何が変わったか・いつ変わったかの質問に使う |
| v2 | 数値の今の値を聞かれたら、項目を1つに決め、経緯を古い順に書き出してから答えさせる | 今の値の質問に使う |
| v3 | 質問の種類を AI に決めさせ、種類ごとに答え方を指示する | 使っていない（今の値を間違えるようになった） |
| auto | 質問の種類をコードで決めて、v1 か v2 を使う | 画面で使う |

auto の流れ:

1. 質問に「何が変わ」「どう変わ」「どう調整」「変更点」「変更内容」「どのパッチ」「いつ」のどれかがあれば v1、なければ v2 を使う（rules.py の choose_prompt）
2. Gemini で回答を作る（temperature 0）
3. 回答に【変更の経緯】の行があれば、一番新しいパッチの「変更後」を【今の値】に入れ直す（rules.py の fix_current_value）。パッチ番号は数値として比べる

モデルの切り替え:

- gemini-3.8-flash → gemini-3.5-flash-lite の順に試す
- 429、500、503 のときだけ次のモデルを試す。それ以外のエラーはそのまま返す
- すべて失敗したら 503 を返す

### 3.6 画面（frontend）

- `/api/ask` を Vite のプロキシで `http://127.0.0.1:8000/ask` に転送する
- 回答に【今の値】の行があれば取り出し、「値（根拠: パッチ〇〇）」を値と根拠に分けて大きく表示する。残りは react-markdown で表示する（HTML はそのまま実行しない）
- 出典の見出しに PvP 系の言葉があれば PvP のラベルを付ける

## 4. 評価と自動テスト

### 4.1 評価（run_eval.py）

| オプション | 内容 |
| --- | --- |
| --model | 使うモデルを1つに固定する（モデルを比べるとき） |
| --prompt | v1 / v2 / v3 / auto |
| --search | vector / hybrid |
| --search-only | AI を使わずに検索だけを測る（回数制限を使わない） |
| --questions | 使う質問のファイル（省略時は eval/questions.jsonl） |

- 1問ごとに5秒あける。混雑（429、500、503）のときは30秒待って、最大3回まで試す
- 1日の回数制限に達したときは、待っても回復しない。429 が何問も続いたら止める
- 結果のファイル名: 「日時_（質問のファイル名_）モデル_プロンプト_検索.jsonl」

### 4.2 自動テスト（pytest）

- AI やデータに依存しない処理だけを、別のファイル（app/rules.py、scripts/grading.py）に分けてテストする。モデルの読み込みも API キーも要らず、1秒かからない
- これまでに見つかった不具合や失敗を、テストとして残している
  - 大分類が変わっても前の中分類が残る、見出しだけの項目が消える（チャンク作り）
  - 経緯は正しいのに今の値を間違える、パッチ番号を文字として比べる（今の値の補正）
  - 「7.2」が「7.25」に一致する、「何が変わったか」に「分かりませんでした」と答える（採点）
- コードを直したら、まず `python -m pytest` を流す

## 5. 改善の記録

| 段階 | 検索@3 | 回答の正解（lite） | 主な変化 |
| --- | --- | --- | --- |
| 最初の版（vector、絞り込みなし、v1） | 87％ | 19/19（q002 は採点外） | |
| PvE／PvP の絞り込み | 93％ | 17/19（v1） | 検索の順位が下がった問題はなし |
| v2 | 93％ | 19/19（q002 は採点外で、実は✕） | 今の値の質問は強くなった |
| v3 | 93％ | 18/20 | q002 は直ったが、q009、q011 が✕ |
| auto | 93％ | 20/20 | v1 と v2 の得意な質問を両方取れた |
| hybrid（検索だけ） | 100％ | － | q016 だけ 1位 → 2位に下がった |

- 回答の正解は、同じ条件でも実行のたびに変わることがある。1回だけの結果で判断しない
- 改善はすべて評価用の20問を見ながら決めた。テスト用の10問で確かめるまでは、この20問だけに効いている可能性がある

## 6. 設計の判断

| 判断 | 理由 |
| --- | --- |
| データは Steam ではなくロードストーンから取る | Steam は概要だけで、大型パッチも取れなかった |
| 取得の前に規約を確認し、1回だけ・5秒間隔で取る | サイトへの負荷と利用条件に配慮するため |
| 見出しの階層を class で決める | タグ名だけでは、大分類（h3）と中分類（h2）の上下が逆になる |
| チャンクに見出しの階層を付ける | どのジョブの話か、PvE か PvP かをチャンクだけで分かるようにするため |
| 表を途中で切らない | スキル名と変更前・変更後が別のチャンクに分かれると、正しく答えられない |
| 見出しだけの項目を残す | 見出しそのものが変更内容になっている項目が、全体の約4分の1あった |
| 埋め込みは無料のローカルモデル | API キーも費用もかからない。後で別のモデルと比べられる |
| PvE と PvP で検索の対象を分ける | 両方で調整されたスキルで、反対側のチャンクが正解を押し下げていた |
| ハイブリッド検索 | 意味の近さだけでは、スキル名の違いをほとんど区別できなかった |
| キーワード検索は2文字ずつの区切り | 追加の辞書が要らず、スキル名のような固有名詞に強い |
| 検索結果をパッチの古い順に並べる | 変更の流れを AI が追いやすくするため |
| 回答の AI は無料枠の Gemini | 費用をかけずに始めるため。混雑に備えて予備のモデルを用意した |
| temperature 0 | 同じ質問になるべく同じ答えを返し、比べやすくするため |
| 質問の種類はコードで決める（auto） | AI に決めさせる v3 では、肝心の答え方の手順が崩れた |
| 今の値はコードで決め直す | AI が正しい経緯を書いたのに、今の値だけを間違えることがあった |
| 検索だけを測るモード | 回数制限を使わずに、検索の改善を何度でも試せる |
| 検索の再現率は順位で測る | 上位8件だけでは100％のままで、改善が数字に出なかった |
| 評価の根拠はチャンク ID ではなくパッチ番号で持つ | チャンクの作り方を変えると ID がずれるため |
| history の質問も採点する | 採点の対象外にしていたら、v2 で答えられなくなったことに気づけなかった |
| テスト用の質問を別に持つ | 同じ質問で直し続けると、その質問だけに効く直し方になるおそれがある |
| AI に依存しない処理を別のファイルに分ける | モデルや API キーなしで、すぐにテストできるようにするため |

## 7. 分かっている課題

| 課題 | 内容 | 対応の予定 |
| --- | --- | --- |
| 1つのセルの複数の変更を読み落とす | 「威力が…。減衰率が…」のように1つのセルに2つの変更があると、軽いモデルが2つ目を読み落とす（q009） | チャンクを作る段階で、セルの中の変更を別々の行に分ける |
| 質問の種類の判定は言葉の一致だけ | 想定と違う言い回しだと、種類を間違える。間違えた場合は v2 になる | 評価用の質問に言い回しの違うものを足して確かめる |
| 採点は数字が入っているかだけ | 【今の値】の行がない回答では、たまたま正解の数字が入っているだけでも◯になる | 必要になったら、AI に採点させる仕組みを作る |
| モデルによるぶれ | lite は実行のたびに✕の問題が入れ替わることがあった | 何回か流して比べる |
| 無料枠の回数制限 | 1日に流せる評価の回数が限られる | 検索の改善は検索だけのモードで試す |
| 新しいパッチ | 自動では取り込まない | 更新の自動化 |
