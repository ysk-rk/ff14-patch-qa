# 設計書：FF14 パッチノート Q&A

最終更新: 2026-11-05

## 1. 全体の構成

```text
[ロードストーン]
     │ ① 取得（23ページを1回だけ）
     ▼
data/raw/lodestone/*.html
     │ ② 本文と表を取り出して分割
     ▼
data/processed/chunks.jsonl（2,932チャンク、うち PvP 403）
     │ ③ 埋め込み
     ▼
data/index/（Chroma）
     │
     ▼
[FastAPI  POST /ask]
     │ ④ 検索（PvE／PvP で絞り込み、vector または hybrid）
     │ ⑤ プロンプトを選ぶ（auto: 質問の言葉で v4 か v5）
     │ ⑥ Gemini で回答
     │ ⑦ 今の値をコードで決め直す（auto のとき）
     ▲
     │ /api/ask（Vite のプロキシ）
[React の画面]
```

| 役割 | 使うもの |
| --- | --- |
| バックエンド | Python 3.12、FastAPI、uvicorn |
| HTML の解析 | Beautiful Soup |
| 埋め込み | intfloat/multilingual-e5-small（sentence-transformers） |
| ベクトルDB | Chroma（ローカルに保存） |
| キーワード検索 | rank-bm25（2文字ずつの区切り） |
| 回答 | Gemini API（google-genai） |
| 自動テスト | pytest、GitHub Actions |
| フロントエンド | TypeScript、React、Vite、ESLint、react-markdown |

## 3. データの流れ

### 3.1 取得（fetch_lodestone.py）

- パッチノート一覧ページに載っている 7.x の23本の URL を、コードに直接書いている
- 1ページごとに5秒あける。保存済みのページは取りに行かない
- User-Agent に個人のポートフォリオ用と分かる文字を入れる

### 3.2 分割（extract_chunks.py）

本文の入れ物は `div.news__detail__wrapper`。見出しは、タグ名と class で次の階層に分ける。

| 階層 | タグ | 例 |
| --- | --- | --- |
| 0 大分類 | h3.mdl-title__ancher | バトル関連、アイテム関連 |
| 1 中分類 | h2 | PvP全般、クエスト関連 |
| 2 項目 | その他の h3 | アクション／特性において、以下の調整が行われます。 |
| 3 ジョブ名など | h4 | モンク |
| 4 | h5 | |

分割のルール:

- 同じ見出しの下にある段落と表を、1,500文字を目安にまとめる
- 表は Markdown の表に変換し、途中で切らない。1,500文字を超える表だけ行の区切りで分け、分けたそれぞれに見出しの行を付け直す
- すべての行が空の列（矢印の画像だけの列）は消す
- 項目以下（階層2以上）の見出しの下に本文も表もなければ、見出しの文を本文として残す
- 各チャンクの先頭に「[パッチ7.2] バトル関連 > … > モンク」の形でパッチ番号と見出しを付ける

チャンクの形（chunks.jsonl の1行）:

| フィールド | 内容 |
| --- | --- |
| id | 「パッチ番号-順番」（例: 7.2-0025）。チャンクの作り方を変えると番号がずれる |
| version | パッチ番号（文字列） |
| order | パッチ番号（数値）。7.05 < 7.1 < 7.11 < 7.2 の順に並ぶ |
| headings | 見出しの階層 |
| has_table | 表を含むか |
| url | 元記事の URL |
| text | 検索と回答に使う本文 |

### 3.3 埋め込み（build_index.py）

- 文書には「passage: 」、質問には「query: 」を付ける（e5 系のモデルの決まり）
- ベクトルは正規化し、Chroma にはコサイン距離で保存する
- 見出しに PvP 系の言葉があるチャンクに `is_pvp` の印を付ける
- 作り直すたびに古いデータを消してから入れ直す

### 3.4 検索（app/rag.py の search）

1. 質問に PvP 系の言葉があれば PvP のチャンクだけ、なければ PvP 以外のチャンクだけを対象にする
2. 検索のしかたに応じて、上位8件を選ぶ（画面では hybrid を使う）
   - vector: 意味の近さの上位8件
   - hybrid: 意味の近さの上位30件と、キーワード検索（BM25、2文字ずつの区切り）の上位30件を、RRF（定数60）で合わせた上位8件
3. それぞれに検索での順位（rank）と意味の近さ（score）を付け、パッチの古い順に並べ替えて返す（変更の流れを AI が追いやすくするため）

ジョブで検索を絞り込む方法は、試して取り消した（6章、7章、notes.md を参照）。

### 3.5 回答（app/rag.py の answer）

ルール:

| 名前 | 内容 | 使うプロンプト |
| --- | --- | --- |
| RULES | 資料にないことは答えない／同じ項目が複数のパッチで変わっていたら一番新しいものを今の情報とする／PvE と PvP を区別する／根拠のパッチ番号を書く | v1、v2、v5 |
| RULES_HISTORY | RULES の2行目だけを「上書きされた変更も省略せず、古い順にすべて書く」に入れ替えたもの | v4 |

プロンプト:

| 名前 | 内容 | 状態 |
| --- | --- | --- |
| v1 | RULES だけを伝えて、すぐに答えさせる | auto では使っていない。前の結果と比べるために残している |
| v2 | 数値の今の値を聞かれたら、項目を1つに決め、経緯を古い順に書き出してから答えさせる | auto では使っていない。前の結果と比べるために残している |
| v3 | 質問の種類を AI に決めさせ、種類ごとに答え方を指示する | 使っていない（今の値を間違えるようになった） |
| v4 | v1 のルールを RULES_HISTORY に入れ替えたもの | 何が変わったか・いつ変わったかの質問に使う |
| v5 | v2 の手順の1と2に、「質問されたジョブ・スキルの資料だけを使う。別のジョブや別のスキルの資料は、同じ項目が書かれていても使わない」を足したもの | 今の値の質問に使う |
| auto | 質問の種類をコードで決めて、v4 か v5 を使う | 画面で使う |

auto の流れ:

1. 質問に「何が変わ」「どう変わ」「どう調整」「変更点」「変更内容」「どのパッチ」「いつ」のどれかがあれば v4、なければ v5 を使う
   - 判定は rules.py の choose_prompt。経緯の質問には "v1"、それ以外には "v2" を返す
   - rag.py の pick_prompt が、"v1" を AUTO_HISTORY_PROMPT（"v4"）に、"v2" を AUTO_CURRENT_PROMPT（"v5"）に置き換える。前の結果と比べるときは、この2つを "v1"、"v2" に戻す
   - answer と show_context.py の両方が pick_prompt を使う。表示されるプロンプトと実際に使うプロンプトがずれないようにするため
2. Gemini で回答を作る（temperature 0）
3. 回答に【変更の経緯】の行があれば、一番新しいパッチの「変更後」を【今の値】に入れ直す（rules.py の fix_current_value）。パッチ番号は数値として比べる
4. 結果には、どのプロンプトを使ったかを「auto(v4)」「auto(v5)」の形で残す

モデルの切り替え:

- gemini-3.8-flash → gemini-3.5-flash-lite の順に試す
- 429、500、503 のときだけ次のモデルを試す。それ以外のエラーはそのまま返す
- すべて失敗したら 503 を返す

### 3.6 画面（frontend）

- `/api/ask` を Vite のプロキシで `http://127.0.0.1:8000/ask` に転送する
- 回答に【今の値】の行があれば取り出し、「値（根拠: パッチ〇〇）」を値と根拠に分けて大きく表示する。残りは react-markdown で表示する（HTML はそのまま実行しない）
- 出典の見出しに PvP 系の言葉があれば PvP のラベルを付ける

## 4. 評価と自動テスト

### 4.1 評価（run_eval.py）

| オプション | 内容 |
| --- | --- |
| --model | 使うモデルを1つに固定する（モデルを比べるとき） |
| --prompt | v1 / v2 / v3 / v4 / v5 / auto |
| --search | vector / hybrid |
| --search-only | AI を使わずに検索だけを測る（回数制限を使わない） |
| --questions | 使う質問のファイル（省略時は eval/questions.jsonl） |

- 1問ごとに5秒あける。混雑（429、500、503）のときは30秒待って、最大3回まで試す
- 1日の回数制限に達したときは、待っても回復しない。429 が何問も続いたら止める
- 503 で失敗した呼び出しも、回数制限に数えられることがある。503 が続いたら1問目で止める
- 結果のファイル名: 「日時_（質問のファイル名_）モデル_プロンプト_検索.jsonl」
- 答えが1つも出なかった結果ファイルは消す（0点に見えてしまうため）。消したことは notes.md に書く
- 一部の問題だけが混雑でエラーになったときは、その問題だけのファイルを作って流し直す（例: retry.jsonl）。評価用の問題に限る

採点:

| 種類 | ◯の条件 |
| --- | --- |
| latest、other_attr_later、pvp_noise | 正解の数字が入っている。【今の値】の行があれば、その行だけを見る |
| history | 「分かりませんでした」と答えておらず、必要なパッチ番号がすべて入っている |
| when | 正解のパッチ番号が入っている |
| unanswerable | 「分かりませんでした」などと答えている |

### 4.2 テスト用の問題の扱い

- 改善を決めるのに使わない問題を、テスト用として別のファイルに持つ
- 結果を見る前にコミットする。最終形が決まってから流し、結果を見て直さない。検索だけのモードでも流さない
- 一度流したテスト用の問題は、評価用に移す。古いファイルは名前を変えて残す（test_questions_2026-10.jsonl）
- 次の改善を確かめるときは、新しいテスト用の問題を作り、直す前にコミットする
- 例外: テスト用の結果を見て直したところがなく、別の評価用の問題から始めた改善なら、同じテスト用の問題をもう1回使ってよい。使う前に、その判断を notes.md に書く
- n001〜n010 は、v4 と v5 の2回使った。次の改善では、新しいテスト用の問題を作る

### 4.3 自動テスト（pytest、GitHub Actions）

- AI やデータに依存しない処理だけを、別のファイル（app/rules.py、scripts/grading.py）に分けてテストする。モデルの読み込みも API キーも要らず、1秒かからない（40個）
- これまでに見つかった不具合や失敗を、テストとして残している
  - 大分類が変わっても前の中分類が残る、見出しだけの項目が消える（チャンク作り）
  - 経緯は正しいのに今の値を間違える、パッチ番号を文字として比べる（今の値の補正）
  - 「7.2」が「7.25」に一致する、「何が変わったか」に「分かりませんでした」と答える（採点）
- rag.py は埋め込みモデルと API キーが要るため、テストの対象にしていない。プロンプトを変えたら、git diff で変えた行だけが変わっていることを確かめる（消えた行の数を見る）
- push のたびに GitHub Actions で、バックエンドのテスト（requirements-test.txt のライブラリだけを入れる）と、画面の lint・ビルドを流す
- コードを直したら、まず `python -m pytest` を流す

## 6. 設計の判断

| 判断 | 理由 |
| --- | --- |
| データは Steam ではなくロードストーンから取る | Steam は概要だけで、大型パッチも取れなかった |
| 取得の前に規約を確認し、1回だけ・5秒間隔で取る | サイトへの負荷と利用条件に配慮するため |
| 見出しの階層を class で決める | タグ名だけでは、大分類（h3）と中分類（h2）の上下が逆になる |
| チャンクに見出しの階層を付ける | どのジョブの話か、PvE か PvP かをチャンクだけで分かるようにするため |
| 表を途中で切らない | スキル名と変更前・変更後が別のチャンクに分かれると、正しく答えられない |
| 見出しだけの項目を残す | 見出しそのものが変更内容になっている項目が、全体の約4分の1あった |
| 埋め込みは無料のローカルモデル | API キーも費用もかからない。後で別のモデルと比べられる |
| PvE と PvP で検索の対象を分ける | 両方で調整されたスキルで、反対側のチャンクが正解を押し下げていた |
| ハイブリッド検索 | 意味の近さだけでは、スキル名の違いをほとんど区別できなかった |
| キーワード検索は2文字ずつの区切り | 追加の辞書が要らず、スキル名のような固有名詞に強い |
| 検索結果をパッチの古い順に並べる | 変更の流れを AI が追いやすくするため |
| 回答の AI は無料枠の Gemini | 費用をかけずに始めるため。混雑に備えて予備のモデルを用意した |
| temperature 0 | 同じ質問になるべく同じ答えを返し、比べやすくするため |
| 質問の種類はコードで決める（auto） | AI に決めさせる v3 では、肝心の答え方の手順が崩れた |
| 今の値はコードで決め直す | AI が正しい経緯を書いたのに、今の値だけを間違えることがあった |
| 経緯の質問は、ルールを入れ替えたプロンプト（v4）で答える | 「新しいパッチを優先する」ルールが、経緯の質問では途中の変更を捨てる原因になった。今の値の質問には、このルールが必要 |
| 別のジョブの資料は、検索で外さず、プロンプト（v5）で使わないよう指示する | AI に渡す資料は8件しかないので、検索で1件外すと別の1件が入り、ほかの問題の資料を押し出した（q024）。プロンプトなら、資料の顔ぶれを変えずに済む |
| 古いプロンプトを書き換えずに、新しいプロンプトを足す | 前の結果をあとから流し直して比べられるようにするため。auto で使うプロンプトは AUTO_HISTORY_PROMPT と AUTO_CURRENT_PROMPT の2つで切り替える |
| プロンプトを選ぶ処理を1か所（pick_prompt）にまとめる | rag.py と show_context.py で別々に書くと、片方だけ直したときに、表示と実際がずれるため |
| AI を呼ばずに資料とプロンプトを見る道具を持つ（show_context.py） | 回数制限を使わずに、答えがおかしい原因を調べられる。q018 の原因はこれで分かった |
| 検索だけを測るモード | 回数制限を使わずに、検索の改善を何度でも試せる |
| 検索の再現率は順位で測る | 上位8件だけでは100％のままで、改善が数字に出なかった |
| 評価の根拠はチャンク ID ではなくパッチ番号で持つ | チャンクの作り方を変えると ID がずれるため |
| history の質問も採点する | 採点の対象外にしていたら、v2 で答えられなくなったことに気づけなかった |
| テスト用の質問を別に持つ | 同じ質問で直し続けると、その質問だけに効く直し方になるおそれがある |
| 使い終わったテスト用の問題は評価用に移し、新しいテスト用の問題を作る | 結果を見た問題は、もう「見ていない問題」として使えないため |
| 直す前に、判断の基準を決めておく | 結果を見てから基準を決めると、都合のよい解釈をしてしまうため |
| 採点で見分けられない悪化は、AI を流す前に取り消してよい | ジョブでの絞り込みでは、q024 の悪化を採点では見分けられなかった（パッチ番号だけで◯になる）。回数制限を使っても判断の材料にならない |
| 3.8-flash が使えないときは lite の結果で判断する | 無料枠の 3.8-flash は混雑で答えが出ないことが多く、待つと作業が止まるため |
| AI に依存しない処理を別のファイルに分ける | モデルや API キーなしで、すぐにテストできるようにするため |
| ライブラリのバージョンを固定する | 数か月後に入れ直しても、同じ環境で動くようにするため |

#### 使う AI モデル

今は Gemini API の無料枠（gemini-3.8-flash、混雑時は gemini-3.5-flash-lite）を使っている。

無料枠の問題:

- 3.8-flash は混雑（503）と回数制限（429）で、答えが出ないことが多い。10月25日から11月5日の間に、答えが出たのは1回だけ
- そのため、v4 と v5 の改善が 3.8-flash でも効いたかを、まだ確かめられていない

決めること:

- 有料にするか。有料にするなら、評価のときだけにするか、画面のアプリも有料にするか
- Gemini の有料枠にするか、別の会社のモデルにするか

分かっていること:

- 同じモデルなら、有料でも無料でも答えは同じ。有料にして良くなるのは、エラーが減ること
- 別の会社に切り替えても、コードの修正は rag.py の AI を呼ぶ部分、requirements.txt、.env のキーの名前だけで済む。検索、プロンプト、rules.py、採点、画面、テストは変えなくてよい
- 時間がかかるのは測り直し。プロンプトは Gemini の失敗を見ながら直してきたので、別のモデルでは答え方の癖が違う。特に、今の値の補正は「【今の値】」と「- パッチ〇〇: 〇〇 → 〇〇」の形で書かれた回答でしか効かない
- 画面のアプリを有料にすると、公開したときに、質問のたびに費用がかかる。README を見た人が無料で試せるよう、Gemini の無料枠は残したい

決めるときに確かめること:

- 各社の料金ページで、今の値段を確かめる
- 有料にするなら、予算の上限と通知を必ず設定する
