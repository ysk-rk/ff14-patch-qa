# 仕様書：FF14 パッチノート Q&A

最終更新: 2026-11-09

## 1. 目的

FINAL FANTASY XIV 黄金のレガシー（パッチ 7.0〜7.57）のパッチノートをもとに、質問に出典付きで答える。

パッチノートは、新しいパッチが古い内容を上書きしていく。このアプリでは、**古い情報を今の情報として答えないこと**を一番の品質目標にする。

## 2. 想定する利用者と使い方

- FF14 のプレイヤーが、スキルの今の性能や、いつ何が変わったかを調べる
- 質問例
  - 今の値: 「モンクの万象闘気圏の今の威力は？」「機工士のエクスカベーターの2体目以降の威力減衰率は？」
  - 何が変わったか: 「PvPのモンクの夢幻闘舞は何が変わった？」
  - いつ変わったか: 「移動しながらマウントを呼び出せるようになったのはどのパッチ？」

## 4. 機能

### 4.1 質問に答える

- 利用者が日本語で質問を入力する
- パッチノートから関連する箇所を検索し、AI が回答を作る
- 回答には、根拠にしたパッチ番号を必ず含める

### 4.2 回答のルール

| ルール | 内容 |
| --- | --- |
| 資料だけで答える | 資料に書かれていないことは答えず、「パッチノートからは分かりませんでした」と答える |
| 新しい情報を優先する（今の値の質問） | 同じ項目が複数のパッチで変わっている場合は、一番新しいパッチの値を今の値として答える |
| 項目ごとに考える（今の値の質問） | 威力・減衰率などの項目ごとに、一番新しい変更を探す。後のパッチで別の項目だけが変わっていても、聞かれた項目の値は変わらない |
| 質問されたジョブ・スキルだけを見る（今の値の質問） | 別のジョブや別のスキルの資料は、同じ項目（威力、最大チャージ数など）が書かれていても使わない |
| 経緯は省略しない（何が変わったかの質問） | あとのパッチで上書きされた変更も省略せず、質問されたスキルや項目の変更を、パッチの古い順にすべて書く |
| PvE と PvP を区別する | 質問に PvP 系の言葉（PvP、フロントライン、クリスタルコンフリクト）がなければ PvE として答える |
| 出典を示す | 根拠にしたパッチ番号を書く |

「新しい情報を優先する」と「経緯は省略しない」は、質問の種類によって使い分ける。経緯の質問に「新しい情報を優先する」をあてはめると、上書きされた途中の変更が回答から抜けるため。

「質問されたジョブ・スキルだけを見る」は、検索では行わない。検索で別のジョブの資料を外すと、AI に渡す8件の顔ぶれが変わり、ほかの質問に必要な資料が押し出されることがあるため。

### 4.3 回答の形

数値の今の値を聞かれた場合は、次の形で答える。

```text
【今の値】25％（根拠: パッチ7.3）
【変更の経緯】
- パッチ7.2: 65％ → 50％
- パッチ7.25: 50％ → 35％
- パッチ7.3: 35％ → 25％
```

- 【今の値】は、【変更の経緯】の中で一番新しいパッチの「変更後」の値にする
- 何が変わったかを聞かれた場合は、ふつうの文章で、変更をパッチの古い順にすべて書く
- いつ変わったかを聞かれた場合は、ふつうの文章で、変わったパッチの番号を答える

### 4.4 画面

- 質問欄と、例の質問ボタン
- 回答
  - 【今の値】があれば、値を大きく表示し、根拠のパッチを添える
  - それ以外の部分は Markdown として表示する（太字、箇条書き）
  - 回答したモデル、使ったプロンプト、検索のしかたを小さく表示する
- 出典
  - 回答に使った資料を、新しいパッチが上に来る順で表示する
  - それぞれに、パッチ番号、PvE／PvP のラベル、見出し、元記事へのリンク、意味の近さを表示する

## 5. API

### POST /ask

リクエスト

```json
{ "question": "機工士のエクスカベーターの2体目以降の威力減衰率は？" }
```

レスポンス（200）

```json
{
  "answer": "【今の値】25％（根拠: パッチ7.3）\n【変更の経緯】\n- パッチ7.2: 65％ → 50％\n- パッチ7.25: 50％ → 35％\n- パッチ7.3: 35％ → 25％",
  "model": "gemini-3.5-flash-lite",
  "prompt": "auto(v5)",
  "search": "hybrid",
  "sources": [
    {
      "version": "7.3",
      "headings": "バトル関連 > アクション／特性において、以下の調整が行われます。 > 機工士",
      "url": "https://jp.finalfantasyxiv.com/lodestone/topics/detail/…/",
      "score": 0.85
    }
  ]
}
```

| フィールド | 内容 |
| --- | --- |
| answer | AI の回答（Markdown） |
| model | 回答したモデル |
| prompt | 使ったプロンプト。auto のときは「auto(v5)」（今の値の質問）「auto(v4)」（何が変わったか・いつ変わったかの質問）の形で、実際に使ったものを示す |
| search | 検索のしかた（vector / hybrid）。画面では hybrid |
| sources | 回答に使った資料（パッチの古い順） |
| sources[].version | パッチ番号 |
| sources[].headings | 見出しの階層（「 > 」区切り） |
| sources[].url | 元記事の URL |
| sources[].score | 質問との意味の近さ（0〜1） |

エラー

| コード | 場合 |
| --- | --- |
| 422 | リクエストの形が正しくない |
| 503 | すべての AI モデルが混雑や回数制限で使えない（detail に理由を入れる） |

## 6. 評価

### 6.1 評価用データ

| ファイル | 問題数 | 使い方 |
| --- | --- | --- |
| eval/questions.jsonl | 44 | 改善を決めるために、何度も流して結果を見る |
| eval/dev_history.jsonl | 6 | questions.jsonl のうち、何が変わったかの質問6問（q002、t008、q021〜q024）。回数制限が厳しいモデルで、経緯の質問だけを確かめるときに使う |
| eval/test_questions.jsonl | 10 | 改善に使っていない質問で、改善が本物かを確かめる。**結果を見て直さない。最終形が決まってから流す** |
| eval/test_questions_2026-10.jsonl | 10 | 使い終わったテスト用データ（t001〜t010）。中身は questions.jsonl に移した。結果ファイルがどの問題で測ったものかを確かめるために残す |
| eval/test_questions_2026-11.jsonl | 10 | 使い終わったテスト用データ（n001〜n010）。同上 |

テスト用データの扱い:

- 結果を見る前にコミットする。検索だけのモードでも、最終形が決まる前には流さない
- 一度流したテスト用の問題は、評価用に移す
- 次の改善を確かめるときは、新しいテスト用の問題を作り、直す前にコミットする
- 例外として、テスト用の結果を見て直したところがなく、別の評価用の問題から始めた改善なら、同じテスト用の問題をもう1回使ってよい。使う前に、その判断を開発メモに書く
- 今のテスト用データ（m001〜m010）は、まだ流していない。次の改善の形が決まってから流す

1行が1問。

| フィールド | 内容 |
| --- | --- |
| id | 問題の ID（評価用は q001〜q024 と、前のテスト用から移した t001〜t010、n001〜n010。テスト用は m001〜m010） |
| question | 質問文 |
| mode | pve / pvp / general（バトル以外）/ none（答えられない） |
| kind | 質問の種類（下の表） |
| shape | 失敗の形の印（なくてもよい）。"q018" は、別のジョブに同じ項目のもっと新しい変更がある問題 |
| expected | 正解 |
| as_of | どのパッチ時点の正解か |
| latest_patch | その項目が最後に変わったパッチ |
| keyword | 根拠の資料に含まれているはずの言葉 |
| evidence_versions | 正解を答えるのに必ず必要なパッチ |
| note | 変更の流れなどのメモ |

| kind | 内容 | 評価用 | テスト用 |
| --- | --- | --- | --- |
| latest | 一番新しい変更がそのまま正解 | 18 | 2 |
| other_attr_later | 後のパッチで別の項目だけが変わっている（q018 と同じ形を含む） | 10 | 3 |
| pvp_noise | PvP の調整が混ざりやすい | 1 | 1 |
| history | 変更の流れ全体を答える | 10 | 2 |
| when | いつ変わったかを答える | 1 | 1 |
| unanswerable | 答えられないことを正しく伝える | 4 | 1 |

テスト用の other_attr_later の3問（m001〜m003）は、すべて q018 と同じ形（shape: "q018"）。

正解の決め方: パッチごとの「変更前」と「変更後」の数字がつながっているかで確かめる。間に見落とした調整があれば、ここがずれる。

### 6.2 評価の指標

| 指標 | 測り方 |
| --- | --- |
| 回答の正解 | 下の採点のしかたで◯の割合 |
| 検索@3 | evidence_versions のパッチで keyword を含む資料が、検索の上位3件に入った割合 |
| 検索@8 | 同じく、上位8件（AI に渡す件数）に入った割合 |

- 検索の指標は、PvE の質問では PvE の資料、PvP の質問では PvP の資料だけを数える
- 指標は kind ごとにも集計する
- 結果は eval/results/ に1問1行で保存する（回答、検索で取った資料の順位を含む）
- 答えが1つも出なかった結果ファイルは消し、消したことを開発メモに書く

採点のしかた:

| kind | ◯の条件 |
| --- | --- |
| latest、other_attr_later、pvp_noise、when | 正解の数字が回答に入っている。【今の値】の行があれば、その行だけを見る |
| history | evidence_versions のパッチ番号がすべて回答に入っていて、「分かりませんでした」と答えていない |
| unanswerable | 「分かりませんでした」などの言葉が回答に入っている |

数字の比べ方: 「1,000」と「1000」、「%」と「％」は同じとして扱う。「7.2」が「7.25」に一致しないよう、数字の前後も見る。

採点の限界: 数字やパッチ番号が入っているかだけを見る。経緯の質問で、パッチ番号は合っていても中身が違う場合は見分けられない。

### 6.3 改善の進め方

- 1回に1つだけ変える
- 変える前に、採用するかを決める基準を書いておく。結果を見てから基準を変えない
- 基準を満たさなかった変更は取り消し、試したことと理由を開発メモに残す
- AI を使わずに確かめられることは、先に確かめる（検索だけのモード、scripts/show_context.py）
- 検索を変えるときは、上位3件だけでなく、上位8件から消えた資料がないかも確かめる

## 7. 制約

- AI は Gemini API の無料枠で使う。混雑（503）や回数制限（429）が起きる。1日の回数制限は、太平洋時間の0時（日本時間17時ごろ。アメリカの夏時間の間は16時ごろ）にリセットされる
- 混雑（503）で失敗した呼び出しも、回数制限に数えられることがある。503 が続いたら早めに止める
- 無料枠に送った内容は Google のサービス改善に使われることがある。公開されているパッチノート以外の情報は送らない
- パッチノートの著作権はスクウェア・エニックスにある。本文は公開しない
- 新しいパッチは自動では取り込まない（今後の作業で対応）

## 8. 設定（backend/.env）

| 名前 | 内容 |
| --- | --- |
| GEMINI_API_KEY | Gemini API のキー。必須。公開しない |
| LLM_PROVIDER | 回答に使う AI の会社。書かなければ gemini。今使えるのは gemini だけ。知らない名前を書くと、最初の質問のときにエラーになる |

- .env は git に入れない
- 別の会社を足したときは、その会社のキーの名前をこの表に足す
